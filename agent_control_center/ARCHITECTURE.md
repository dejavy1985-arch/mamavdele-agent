# agent_control_center: архитектура (этап 1)

Личный центр управления вашими агентами из одного чата в Telegram. Вы пишете
боту обычным текстом, он определяет проект, передаёт задачу нужному агенту,
ведёт журнал и честно сообщает, если проект неясен или не подключён.

Документ описывает: что уже сделано и проверено, как устроена изоляция, откуда
взяты идеи и где проходят честные границы возможного на этом этапе.

## 1. Что это НЕ трогает

Действующий агент `mamavdele-agent` (модерация комментариев Instagram/Facebook:
вебхук Meta, черновик от LLM, карточка одобрения в Telegram, отправка ответа
после одобрения) остаётся как есть. Центр управления добавлен отдельной папкой
`agent_control_center/` и не меняет ни один файл существующего агента, его
процессы, токены и настройки.

## 2. Модель «домиков»

Каждый проект живёт в своём домике: отдельная папка со своим манифестом,
памятью, входящими поручениями, журналом и секретами.

```
agent_control_center/
  acc/                     ядро (без сторонних зависимостей)
  homes/
    mamavdele-agent/
      manifest.json        описание проекта, ключевые слова, адаптер, статус
      inbox/               поручения от центра (создаётся при работе)
      memory/              долговременная память проекта
      secrets/             секреты проекта (в git не попадают)
    content-studio/
      ...
  config/                  конфиг центра (allowlist, флаги)
  tests/                   офлайн-тесты
  scripts/                 init_homes.py
```

Добавить проект значит добавить папку с `manifest.json`. Код при этом не меняется.

## 3. Изоляция (техническая, не текстовая)

Требование: один агент не может читать или менять файлы другого. Реализовано в
`acc/paths.py`:

- у каждого проекта свой `ProjectSandbox`, привязанный только к корню его домика;
- любой путь разрешается через `safe_resolve`, который:
  - отклоняет абсолютные пути (`/etc/passwd`);
  - отклоняет переходы вверх (`..`) ещё до обращения к диску;
  - отклоняет пути с `~` и с нулевым байтом;
  - проверяет итог по реальному пути (`os.path.realpath`), поэтому ловит
    символические ссылки, ведущие наружу или в соседний домик;
  - при записи дополнительно отказывается писать сквозь существующий симлинк и
    проверяет, что родительская папка внутри домика;
- `assert_isolated` при загрузке проверяет, что домики не вложены друг в друга.

Изоляция подтверждена тестами `tests/test_paths.py`: абсолютный путь, `..`,
глубокий `..`, симлинк в `/etc`, симлинк в соседний домик, префикс-ловушка
(`projectA-extra` не считается частью `projectA`), кросс-доступ между двумя
sandbox всеми способами. Все проходят.

## 4. Компоненты ядра

| Модуль | Роль |
| --- | --- |
| `paths.py` | изоляция файлового доступа (см. выше) |
| `registry.py` | чтение и валидация манифестов домиков, статусы проектов |
| `security.py` | allowlist: команды только от разрешённых Telegram user_id |
| `router.py` | определение проекта по тексту (ключевые слова и псевдонимы) |
| `guardrails.py` | границы этапа 1 (запрещённые) и опасные действия (требуют подтверждения) |
| `audit.py` | журнал действий и ошибок (append-only JSONL) |
| `state.py` | смещение Telegram для восстановления после перезапуска |
| `store_db.py` | SQLite: очередь поручений, статусы, история, дескриптор сессии |
| `adapters.py` | доставка задачи агенту проекта (manual / cross_session) |
| `dispatcher.py` | связывает всё: allowlist, команды, границы, подтверждение, маршрут, очередь, журнал |
| `cli.py` | офлайн-инструменты без Telegram: doctor, route, send, queue, history, add-home, demo |
| `telegram_bot.py` | локальный транспорт Telegram (long polling, stdlib) |

## 5. Маршрутизация и уточнение

`router.py` считает совпадения ключевых слов и псевдонимов из манифестов:

- уверенный лидер с отрывом это `MATCH`;
- близкие кандидаты это `AMBIGUOUS`, бот просит уточнить;
- ноль совпадений это `UNKNOWN`, бот предлагает `/projects`.

Если проект найден, но его статус не `connected`, бот честно сообщает, что
проект не подключён, и задачу не передаёт. Логика прозрачная и офлайновая; позже
можно добавить LLM-классификатор вторым слоем, не меняя интерфейс.

## 6. Восстановление после перезапуска

`state.py` хранит смещение обработанных сообщений Telegram (`update_id`),
незавершённые задачи и последнее состояние проектов. Запись атомарная (временный
файл плюс `rename`). При старте новый экземпляр читает тот же файл и продолжает с
той же точки, поэтому перезапуск программы или компьютера не теряет прогресс и не
дублирует уже обработанные сообщения. Журнал `audit.jsonl` только дописывается,
история переживает перезапуск. Проверено в `tests/test_state.py`.

Действующие процессы агентов при этом продолжают работать: центр их не
останавливает и не перезапускает.

## 7. Границы первого этапа (жёсткие)

Центр НЕ публикует контент, не пишет клиентам, не проводит платежи, не меняет
токены, доступы и настройки агентов. Это не только текст:

1. в коде центра нет ни одной функции с такими действиями. Адаптеры (`adapters.py`)
   только записывают поручение в домик проекта или готовят передачу текста в
   сессию. Отправок во внешние сервисы в центре нет;
2. `guardrails.py` распознаёт запрос на запрещённое действие и помечает решение
   как `boundary_blocked`; диспетчер такое не выполняет и честно отвечает.

Проверено в `tests/test_guardrails.py` и `tests/test_dispatcher.py`.

## 8. Что взято из изученных проектов (и что нет)

Все три репозитория доступны и под лицензией MIT. Идеи заимствованы, код не
копировался.

- `jflaflamme/claude-commander` (MIT): ближе всего к задаче. Взяты идеи: allowlist
  по одному admin-аккаунту, реестр проектов, восстановление состояния между
  перезапусками, авто-маршрутизация по проектам. Их прямая зависимость от Claude
  Agent SDK и постоянных подпроцессов на этапе 1 не берётся ради простоты
  обслуживания.
- `asianviking/pochi` (MIT): взята идея «папка равна изолированному домику со своим
  конфигом». Их модель «тема Telegram на каждую папку» и мульти-движки (Codex,
  OpenCode) на этапе 1 не нужны.
- `NousResearch/hermes-agent` (MIT): взяты идеи слоя памяти на проект и явного
  подтверждения опасных действий. Сам агент слишком большой (300+ моделей, семь
  бэкендов, свой TUI), копировать его для нашей задачи нецелесообразно.

## 9. Cross-session messaging: где помогает и где предел

Официальная функция обмена сообщениями между сессиями (`ListAgents` и
`SendMessage`) подходит как механизм передачи поручения в живую сессию проекта,
но у неё есть реальные ограничения, важные для нашей задачи:

- передаётся только простой текст, не файлы и не контекст;
- облачная сессия видит сессии на другой машине только при подключённом Remote
  Control; без него сообщение уходит без адреса для ответа, то есть ответ обратно
  не гарантирован;
- это механизм поручения и уведомления, а не удалённый вызов с гарантированным
  результатом.

Поэтому на этапе 1 основной адаптер это `manual` (поручение кладётся в домик
проекта), а `cross_session` реализован честно: он проверяет доступность и, если
её нет, возвращает `not_available`, не выдумывая ни отправку, ни ответ. Включение
живой передачи это локальный шаг на вашем компьютере (см. README).

## 10. Подключение проектов

Домики сейчас это тестовый каркас, не подключённые агенты:

- `mamavdele-agent`: реальный проект, код изучен, но как живой агент к центру пока
  НЕ подключён (статус `registered`).
- `example-template`: образец формата манифеста, не реальный агент.

Второй реальный проект НЕ выбран заранее. Его выберем после осмотра ваших папок на
компьютере, из того, что там реально есть.

Границы честности: из облачной сессии нет доступа к папкам вашего компьютера и к
вашим локальным (bridge) сессиям (сейчас offline). Поэтому осмотр реальных папок,
живой запуск бота и передача задач в локальные сессии выполняются на вашей машине.
Установка под Windows описана в `INSTALL_WINDOWS.md`, разбор Jarvis в
`RESEARCH_JARVIS.md`.

## 11. Подтверждение опасных действий и очередь

Опасное, но разрешённое действие (удалить, перезаписать, сбросить, выкатить)
диспетчер не выполняет сразу: он ставит задачу в статус ожидания и просит `/confirm`
или `/reject`. Это аналог Plan Mode и подтверждения инструментов в Jarvis. Обычные
поручения проходят в очередь на SQLite со статусами (`queued`, `processing`, `done`,
`failed`, `rejected`), а история событий доступна по `/history`. Всё это переживает
перезапуск, потому что хранится в файле базы, а не в памяти процесса.
