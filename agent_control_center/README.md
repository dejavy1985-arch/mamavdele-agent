# agent_control_center

Личный центр управления вашими агентами из одного Telegram-чата. Вы пишете боту
обычным текстом, он определяет, к какому проекту относится запрос, передаёт
задачу нужному агенту и возвращает ответ. Если проект неясен, бот уточняет. Если
проект не подключён, честно сообщает об этом.

Проект добавлен отдельной папкой и НЕ меняет действующего агента `mamavdele-agent`.

## Что уже работает и проверено (офлайн, без интернета)

- Изоляция домиков: один проект не может читать или менять файлы другого. Закрыты
  абсолютные пути, переходы `..`, симлинки наружу и в соседние папки.
- Реестр проектов из манифестов, статусы, allowlist по Telegram user_id.
- Маршрутизация по тексту: точный проект, уточнение при неоднозначности, честный
  ответ «не подключён» и «не понял».
- Границы этапа 1: центр не публикует, не пишет клиентам, не платит, не меняет
  токены. Запрос на такое не выполняется.
- Очередь поручений и статусы на SQLite, история событий, восстановление после
  перезапуска (см. `acc/store_db.py`).
- Подтверждение опасных действий: рискованный запрос (удалить, перезаписать,
  выкатить) сначала спрашивает `/confirm` или `/reject` и только потом передаётся.
- Команды: `/projects`, `/status`, `/queue`, `/history`, `/log`, `/confirm <id>`,
  `/reject <id>`, `/help`.

Идеи и модель данных сверены с Jarvis по его исходному коду (см. `RESEARCH_JARVIS.md`).

Запуск тестов:

```bash
cd agent_control_center
python3 tests/run_tests.py
```

Ожидаемо: 76 тестов, все проходят. Сторонние пакеты не нужны, только Python 3.10+.

## Домики сейчас

- `mamavdele-agent`: реальный проект, код изучен, но как живой агент к центру пока
  НЕ подключён (статус `registered`).
- `example-template`: образец формата домика, не реальный агент.

Это тестовый каркас, а не подключённые агенты. Второй реальный проект выберем после
осмотра ваших папок на компьютере, без навязывания.

## Проверка без Telegram (командная строка)

Всё ядро проверяется офлайн, без токена и без доступа к действующим агентам:

```bash
python3 -m acc.cli doctor                    # самопроверка конфига, домиков, изоляции
python3 -m acc.cli projects                  # список домиков и статусов
python3 -m acc.cli route "сделай выгрузку"    # какой проект выберется (без передачи)
python3 -m acc.cli send --user 111 "текст"    # полный прогон через диспетчер
python3 -m acc.cli queue                      # очередь поручений
python3 -m acc.cli history                    # история событий
python3 -m acc.cli demo                        # прогон на ВРЕМЕННЫХ тест-проектах
```

Команда `demo` создаёт временные тестовые проекты, показывает маршрут, уточнение,
границы, подтверждение и изоляцию (чужое поручение не попадает в соседний домик) и
затем удаляет их. Реальные домики не затрагиваются и не называются подключёнными.

Добавить проект без правки ядра: см. `ADDING_PROJECTS.md` (или
`python3 -m acc.cli add-home ...`).

## Перенос в отдельную папку (Windows или Linux/Beget)

Папка `agent_control_center` самодостаточна и не зависит от кода действующего
агента. Пути внутри считаются от корня проекта, а не от места запуска, поэтому
перенос это просто копирование папки:

1. Скопируйте папку `agent_control_center` в отдельное место (на Windows, например,
   `C:\Users\Вы\agent_control_center`; на Linux/Beget, например, `~/agent_control_center`).
2. Один раз подготовьте: на Windows запустите `scripts\setup_windows.ps1`; на Linux
   выполните `python3 scripts/init_homes.py` и `python3 tests/run_tests.py`.
3. Впишите свой Telegram user_id в `config/control_center.json`.
4. Ядро (`acc/`) при переносе и подключении реальных домиков переписывать не нужно.

Ядро на чистом Python из стандартной библиотеки, поэтому одинаково работает и на
вашем Windows, и позже на сервере Beget. Токен и ключи в GitHub не хранятся.

## Границы первого этапа

Центр НЕ делает сам: публикацию контента, переписку с клиентами, платежи, смену
токенов, доступов и настроек агентов. Это ограничение в коде, а не только в тексте
(см. `ARCHITECTURE.md`, разделы 3 и 7).

## Что нельзя сделать из облачной сессии (честно)

Эта работа велась в облачной сессии. Из неё:

- нет доступа к папкам вашего компьютера;
- нет доступа к вашим локальным (bridge) сессиям Claude Code, сейчас они offline;
- поэтому живой Telegram-бот и передача задач в локальные сессии запускаются на
  вашей машине, а не из облака.

Всё, что можно было проверить без вашего компьютера, реализовано и покрыто
тестами. Живая передача в сессию (`cross_session`) реализована честно: без доступа
она отвечает «недоступно» и не имитирует ни отправку, ни ответ.

## Установка на Windows

Пошаговая инструкция без команд `cp` и `export`: см. `INSTALL_WINDOWS.md`.
Кратко: поставить Python, запустить `scripts\setup_windows.ps1` (проверит Python,
создаст конфиг, заведёт домики, прогонит тесты), вписать свой user_id в
`config\control_center.json`. Telegram на этом этапе не включаем.

Токен бота (когда дойдём до Telegram) кладётся в файл `config\telegram_token.txt`,
он в git не попадает. Переменная окружения `ACC_TELEGRAM_BOT_TOKEN` тоже
поддерживается, но под Windows проще файл.

## Апгрейд: живая передача в сессию Claude Code (позже)

Когда захотите, чтобы бот не просто складывал поручение в домик, а передавал его в
запущенную сессию проекта:

1. Запускайте центр на компьютере с подключённым Remote Control.
2. Подтвердите имя целевой сессии и впишите его в `planned_adapter` манифеста,
   переключив `adapter.type` на `cross_session`.
3. Поставьте `cross_session_available: true` в конфиге.

Помните ограничение функции: между сессиями передаётся только текст, а гарантии
ответа обратно нет без Remote Control. Это механизм поручения, а не удалённый
вызов с гарантированным результатом.

## Структура

См. `ARCHITECTURE.md`. Кратко: `acc/` это ядро, `homes/` это домики проектов,
`config/` это настройки центра, `tests/` это офлайн-тесты, `scripts/` это утилиты.
